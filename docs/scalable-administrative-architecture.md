# Scalable Administrative Hierarchy Architecture

**GramSevak Weather Downscaling System**  
**Phase 3 Technical Architecture Specification**  
*Document Version: 1.0.0 | Date: 2026-09-25*

---

## 1. Executive Summary

Phase 3 establishes a canonical, normalized, database-backed administrative hierarchy:

$$\text{District} \longrightarrow \text{Block} \longrightarrow \text{Panchayat} \longrightarrow \text{Forecast} \longrightarrow \text{Advisory}$$

This architecture replaces hardcoded district assumptions and flat list limitations with a multi-district relational foundation supporting **Nashik**, **Pune**, and future districts across Maharashtra and India. It preserves 100% backward compatibility with existing React (`officer_dashboard`) and Flutter (`farmer_app`) frontends while introducing bounded pagination, database-backed search, and composite indexing.

---

## 2. Canonical Administrative Hierarchy

```
Districts (districts)
  │
  └── Blocks / Tehsils (blocks)
        │
        └── Gram Panchayats (panchayats)
              │
              ├── Station Ground Observations (weather_observations)
              ├── Downscaled Weather Forecasts (downscaled_forecasts)
              └── Agro-Meteorological Advisories (advisories)
```

### Relational Schema Design

#### 1. Districts (`districts`)
* **`id`** (`BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`): System district identifier.
* **`name`** (`TEXT UNIQUE NOT NULL`): District name (e.g. `Nashik`, `Pune`). Indexed.
* **`state`** (`TEXT NOT NULL DEFAULT 'Maharashtra'`): State entity.
* **`created_at`** (`TIMESTAMPTZ DEFAULT NOW()`): Creation timestamp.

#### 2. Blocks (`blocks`)
* **`id`** (`BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`): System block/taluka identifier.
* **`district_id`** (`BIGINT REFERENCES districts(id) ON DELETE RESTRICT`): Foreign key to parent district.
* **`name`** (`TEXT NOT NULL`): Block name (e.g. `Baglan`, `Dindori`, `Haveli`, `Baramati`).
* **`created_at`** (`TIMESTAMPTZ DEFAULT NOW()`): Creation timestamp.
* **Constraint**: `UNIQUE (district_id, name)`.

#### 3. Panchayats (`panchayats`)
* **`id`** (`BIGINT PRIMARY KEY`): Unique system Panchayat identifier (e.g. `1001`, `2001`). Matches legacy `panchayat_id`.
* **`lgd_code`** (`BIGINT NOT NULL`): Official Local Government Directory code. Indexed.
* **`panchayat_code`** (`TEXT`): Administrative code.
* **`name`** (`TEXT NOT NULL`): Panchayat name (e.g. `Ajmer Saundane`). Indexed.
* **`block_id`** (`BIGINT REFERENCES blocks(id) ON DELETE RESTRICT`): Foreign key to parent block.
* **`district_id`** (`BIGINT REFERENCES districts(id) ON DELETE RESTRICT`): Foreign key to parent district.
* **`latitude`** (`NUMERIC`): WGS84 latitude.
* **`longitude`** (`NUMERIC`): WGS84 longitude.
* **`elevation_m`** (`NUMERIC`): Elevation above sea level in meters.
* **`created_at`** (`TIMESTAMPTZ DEFAULT NOW()`): Record timestamp.

## 3. Data Integrity & Duplicate Code Handling

An audit of live government revenue records in Maharashtra revealed critical domain findings:
1. **Panchayat ID Uniqueness**:
   - `id` / `panchayat_id` is 100% unique across all 2,726 Panchayats in Nashik and Pune.
2. **LGD Code Reality**:
   - In Nashik district, 208 records legitimately share parent LGD codes across multi-hamlet revenue clusters (e.g. Kundewadi in Niphad shares LGD 183478, Gilane and Gigaon in Malegaon share LGD 183181).
   - In Pune district, all 1,338 Panchayats have distinct LGD codes.
   - **Resolution**: Strict adherence to domain safety: `panchayats.id` is the primary key; `lgd_code` has a non-unique lookup index (`idx_panchayats_lgd_code_lookup`). No valid revenue data was altered or discarded.
3. **Block-District Membership**:
   - Every block belongs to exactly one district.
   - Every panchayat belongs to exactly one block and one district.
   - Zero orphaned panchayats exist in the database.

## 4. Database Indexing Strategy

To guarantee sub-second queries across thousands of Panchayats and multi-gigabyte weather observations, composite and functional indexes were deployed via migration `20260925000002_hierarchical_indexes.sql`:

| Table | Index Name | Columns / Expression | Operation Accelerated |
| :--- | :--- | :--- | :--- |
| `panchayats` | `idx_panchayats_block_name` | `(block_id, name)` | Block-scoped panchayat listing & alphabetical sort |
| `panchayats` | `idx_panchayats_block_id_id` | `(block_id, id)` | Block-scoped deterministic pagination |
| `panchayats` | `idx_panchayats_district_name`| `(district_id, name)` | District-scoped panchayat aggregation & filters |
| `panchayats` | `idx_panchayats_lower_name` | `(lower(name))` | Case-insensitive prefix/infix village name search |
| `panchayats` | `idx_panchayats_lgd_code_lookup` | `(lgd_code)` | Fast resolution by official census LGD code |
| `blocks` | `uq_blocks_district_name` | `(district_id, name)` | District-to-block resolution & uniqueness |
| `districts` | `idx_districts_name` | `(name)` | District lookup by name |

## 5. API Endpoints Specification

### 1. List Districts
* **Endpoint**: `GET /api/v1/districts`
* **Response**:
```json
[
  { "id": 1, "name": "Nashik", "state": "Maharashtra" },
  { "id": 4, "name": "Pune", "state": "Maharashtra" }
]
```

### 2. List Blocks for District
* **Endpoint**: `GET /api/v1/districts/{district_id}/blocks`
* **Path Parameter**: `district_id` (integer, e.g. 1)
* **Response**:
```json
[
  { "id": 1, "district_id": 1, "name": "Baglan" },
  { "id": 2, "district_id": 1, "name": "Chandwad" },
  { "id": 4, "district_id": 1, "name": "Dindori" }
]
```
* **Error**: HTTP 404 if `district_id` does not exist.

### 3. List Panchayats for Block (Hierarchical)
* **Endpoint**: `GET /api/v1/blocks/{block_id}/panchayats`
* **Query Parameters**:
  * `page` (integer, default `1`, minimum `1`)
  * `page_size` (integer, default `50`, maximum `200`)
  * `search` (string, optional, case-insensitive)
* **Response**:
```json
{
  "total": 167,
  "page": 1,
  "page_size": 50,
  "total_pages": 4,
  "items": [
    {
      "id": 1001,
      "lgd_code": 182597,
      "name": "Ajmer Saundane",
      "block_id": 1,
      "district_id": 1,
      "latitude": 20.6385,
      "longitude": 74.1201,
      "elevation_m": 585.0,
      "panchayat_id": 1001,
      "panchayat_name": "Ajmer Saundane"
    }
  ]
}
```
* **Error**: HTTP 404 if `block_id` does not exist.

### 4. Single Panchayat Detail Lookup
* **Endpoint**: `GET /api/v1/panchayats/{panchayat_id}`
* **Response**: Returns both canonical hierarchical fields (`id`, `name`, `block_id`, `district_id`) and legacy fields (`panchayat_id`, `panchayat_name`, `block_name`, `district_name`, `latitude`, `longitude`, `elevation_m`).
* **Error**: HTTP 404 if not found.

### 5. Legacy Panchayats Endpoint (Backward Compatible)
* **Endpoint**: `GET /api/v1/panchayats`
* **Query Parameters**: `district_name`, `district_id`, `block_name`, `block_id`, `search`, `page`, `page_size`.
* Preserves contract with React dashboard and Flutter mobile app.

## 6. Nashik Completeness & Root Cause Analysis

### Identified Discrepancy
In earlier frontend versions, only 7 blocks were displayed in `DemoPanchayatSelector.tsx`, making Panchayats in 8 Nashik blocks appear missing from the user interface.

### Root Cause
1. **Frontend Hardcoding**: `DemoPanchayatSelector.tsx` contained a static array:
   ```typescript
   const availableBlocks = ['ALL', 'Baglan', 'Dindori', 'Surgana', 'Igatpuri', 'Kalwan', 'Niphad', 'Sinnar'];
   ```
   This excluded Chandwad, Deola, Malegaon, Nandgaon, Nashik, Peint, Trimbakeshwar, and Yevla.
2. **Database Verification**:
   - The PostgreSQL database contains all **15 blocks** and all **1,388 Panchayats** for Nashik.
   - All 1,388 Panchayats are mapped to their respective blocks.

### Permanent Resolution
- Replaced the hardcoded block array with dynamic loading from `GET /api/v1/districts/1/blocks`.
- Provided a full 15-block fallback in `DemoPanchayatSelector.tsx` for offline resilience.
- All 1,388 Panchayats across all 15 blocks of Nashik are now discoverable and searchable.

## 7. Pune Multi-District Support

Pune follows identical relational semantics without any district-specific hardcoding:
- **District**: Pune (ID 4)
- **Blocks**: 13 administrative tehsils (Ambegaon, Baramati, Bhor, Daund, Haveli, Indapur, Junnar, Khed, Mawal, Mulshi, Pune City, Shirur, Velhe).
- **Panchayats**: 1,338 Gram Panchayats.
- **Dynamic Resolution**: Endpoint `GET /api/v1/forecast/panchayat/{panchayat_id}` queries the normalized hierarchy rather than assuming "Nashik", allowing Pune forecasts and advisories to flow through identical pathways.

## 8. Performance Considerations

1. **Bounded Data Transfers**:
   - Page sizes are strictly bounded (`le=200` in block panchayats, `le=500` in legacy).
   - Endpoints return only necessary metadata (excluding heavy weather observation tables).
2. **Avoidance of N+1 Queries**:
   - Single-query count and limit/offset execution.
   - Eager joins and foreign key indexes prevent table scans.
3. **Caching Strategy**:
   - Administrative hierarchy (`districts` and `blocks`) changes rarely.
   - Future CDN / HTTP cache headers (`Cache-Control: public, max-age=86400`) can be added safely at the reverse proxy layer without application changes.
